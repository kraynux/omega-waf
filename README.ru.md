**Omega-Waf** — это единый Lua-скрипт (`omega-waf.lua`) без внешних зависимостей, предназначенный для выполнения при каждом HTTP-запросе веб-сервером, совместимым с `mod_magnet` (нативно lighttpd, либо omega-serv через его мост совместимости `magnet`). Он анализирует путь, запрос и, для POST, тело запроса на предмет известных сигнатур атак (SQL-инъекция, XSS, инъекция команд, обход каталогов), применяет ограничение частоты запросов, управляет постоянным чёрным списком с постепенной эскалацией и логирует каждое решение.

Никакой установки в классическом смысле: один файл, который нужно разместить и указать в конфигурации сервера — и всё.

## Обзор

### Цели

- Фильтровать вредоносные запросы как можно ближе к серверу, до того как они достигнут обслуживаемого приложения.
- Оставаться единым, читаемым файлом без внешних зависимостей и этапа сборки.
- Никогда не приводить к падению веб-сервера: любая внутренняя ошибка скрипта перехватывается и логируется, а не распространяется дальше.
- Ограничивать затраты CPU/памяти на запрос (временные кэши, чтение тела кусками, ограниченная глубина декодирования).
- Предлагать постепенную эскалацию (предупреждение, затем бан) вместо немедленного жёсткого бана при первом незначительном инциденте.

### Что делает Omega-Waf

- Блокирует уже забаненные IP-адреса (постоянный чёрный список на диске), с исключением для явно разрешённых путей (CSS страницы ошибки и т. д.).
- Отслеживает набор чувствительных путей (`.git`, `.env`, `wp-admin`, `phpmyadmin`, `.DS_Store` и т. д.) и отвечает либо HTML-страницей предупреждения, либо прямым баном при повторении.
- Обнаруживает User-Agent, известные как инструменты сканирования или нежелательные боты (sqlmap, nmap, nikto, dirbuster, обычные краулеры...).
- Применяет глобальное ограничение частоты запросов по IP для всех маршрутов.
- Применяет выделенную, более мягкую политику для маршрутов поисковой системы SearXNG (избегает ложных срабатываний на легитимных поисковых запросах, содержащих слова, похожие на атаку).
- Проверяет путь и query-строку (SQLi, XSS, обход каталогов, нулевой байт).
- Проверяет тело POST-запросов (SQLi, XSS, инъекция команд, обход каталогов) с системой накопительной оценки.
- Управляет постепенной эскалацией: единичное подозрительное поведение вызывает оповещение или разовый отказ; повторение в пределах временного окна приводит к окончательному бану.
- Логирует каждое решение (оповещения, добавления в чёрный список) в текстовом или JSON-формате.
- Работает как в нативном lighttpd (жёстко заданные пути), так и встроенным в omega-serv (пути, получаемые динамически из конфигурации сервера).

### Чего скрипт не делает

- Не заменяет специализированный WAF корпоративного уровня (ModSecurity, Coraza, облачный WAF): сигнатуры намеренно простые (сопоставление шаблонов Lua, а не настоящий движок правил PCRE).
- Не анализирует HTTP-заголовки по отдельности, кроме User-Agent.
- Не декодирует тела multipart/form-data и сжатые (gzip) тела — проверка выполняется над полученным необработанным текстом.
- Никогда не проверяет тело запроса, отличного от POST.
- Не выполняет никакого обнаружения инъекции команд в пути URL (осознанный выбор, см. [Известные ограничения](#известные-ограничения-и-то-что-вне-рамок)).
- Не предоставляет никакого интерфейса администрирования: настройка выполняется редактированием переменных в начале файла, чёрный список и whitelist — через простые текстовые файлы.
- Не управляет самостоятельно ротацией своих журналов.

### Предупреждение об использовании

Предоставленные сигнатуры нацелены на распространённые семейства атак, но не являются исчерпывающей защитой. Слишком низкий порог обнаружения на сайте с необычным трафиком (технический поиск, документация, содержащая shell-команды и т. д.) может порождать ложные срабатывания — соответствующим образом настройте `waf_score_threshold` и белый список путей. Всегда тестируйте изменение сигнатуры или порога в некритичной среде перед развёртыванием в продакшене.

## Установка

### Предварительные требования

- Веб-сервер, предоставляющий интерфейс, совместимый с `mod_magnet`:
  - **lighttpd** с включённым модулем `mod_magnet` (`server.modules += ("mod_magnet")`), или
  - **omega-serv** с установленным дополнением `magnet` (`pip install -e ".[magnet]"`, зависимость `lupa` — см. руководство omega-serv, раздел WAF Magnet).
- Встроенный интерпретатор Lua, предоставляемый хостом (lighttpd включает собственный Lua; omega-serv включает `lupa`, системный интерпретатор `lua` не требуется ни в одном из случаев).

### Настройка

1. Скопируйте `omega-waf.lua` в место, доступное для чтения сервером (например, `secure/waf/scripts/omega-waf.lua` для структуры в стиле omega-serv, или любой путь для нативного lighttpd).
2. Создайте каталоги/файлы, ожидаемые конфигурацией по умолчанию (см. [Конфигурация](#конфигурация)):
   ```bash
   mkdir -p secure/waf/magnet-rules.d var/log var/cache
   touch secure/waf/magnet-blocklist.txt
   ```
3. Укажите скрипт в конфигурации сервера:
   - **lighttpd**:
     ```
     magnet.attract-physical-path-to = ( "/путь/к/omega-waf.lua" )
     ```
   - **omega-serv**: включите WAF Magnet в специальном экране TUI (Активная безопасность → WAF → Magnet), который указывает на скрипт и автоматически инжектирует таблицу `omega_magnet_paths` (см. [Совместимость](#совместимость)).
4. Перезапустите (не перезагрузите — перезагрузка никогда не перечитывает уже персистентный Lua-скрипт в памяти) соответствующий сервер.

## Конфигурация

Все настройки задаются прямым редактированием локальных переменных в начале файла (раздел `CONFIGURATION`, строки ~24-70). Отдельного файла конфигурации нет.

| Переменная | Роль | Значение по умолчанию |
|---|---|---|
| `blocklist_file` | Текстовый файл окончательно забаненных IP (один IP на строку, `#` для комментариев) | `secure/waf/magnet-blocklist.txt` |
| `waf_rules_dir` | Каталог внешних правил (содержит `whitelist_paths.txt`) | `secure/waf/magnet-rules.d/` |
| `alerts_log` | Журнал оповещений (обнаружения, отказы, превышения) | `var/log/waf-magnet-alerts.log` |
| `blocklist_log` | Отдельный журнал добавлений в чёрный список | `var/log/waf-magnet-blocklist.log` |
| `rate_store_file` | Файл персистентности счётчиков (rate limit / рецидив), формат таблицы Lua | `var/cache/waf-magnet-rate_store.lua` |
| `enable_body_inspection` | Включает проверку тела POST-запросов | `true` |
| `enable_rate_limit` | Включает ограничение частоты запросов (глобальное + SearXNG) | `true` |
| `enable_auto_block` | Разрешает автоматическое добавление в чёрный список | `true` |
| `use_json_logs` | Переключает журналы оповещений на JSON (иначе читаемый текст) | `false` |
| `waf_score_threshold` | Минимальная накопленная оценка для отказа в POST-запросе | `5` |
| `body_max_inspect` | Максимальный проверяемый размер тела (байты) | `65536` (64 Кб) |
| `chunk_size` | Размер блоков чтения тела | `8192` (8 Кб) |
| `global_rate_max_req` / `global_rate_window` | Квота и окно (с) глобального ограничения частоты по IP | `60` запросов / `60` с |
| `searx_rate_max_req` / `searx_rate_window` | Квота и окно (с) ограничения частоты, выделенного для маршрутов SearXNG | `40` запросов / `60` с |
| `searx_max_query_len` | Максимальный допустимый размер query-строки на маршрутах SearXNG | `4096` символов |
| `suspicious_threshold` | Количество подозрительных попаданий до окончательного бана | `3` |
| `suspicious_window` | Скользящее окно (с), в пределах которого считаются подозрительные попадания | `300` (5 мин) |
| `blocklist_refresh_interval` | Интервал (с) перечитывания файла чёрного списка | `5` |
| `whitelist_refresh_interval` | Интервал (с) перечитывания whitelist путей | `15` |

Под omega-serv первые 5 путей (`blocklist_file`, `waf_rules_dir`, `alerts_log`, `blocklist_log`, `rate_store_file`) автоматически заменяются на настроенные в экране WAF Magnet (глобальная таблица `omega_magnet_paths`, инжектируемая заранее) — жёстко заданные значения выше служат лишь резервом, если эта таблица отсутствует.

> ⚠️ **Эти 5 значений по умолчанию скопированы с собственной структуры каталогов omega-serv** (`secure/waf/...`, `var/log/...`, `var/cache/...`, относительные пути, разрешаемые относительно рабочего каталога проектного типа) — они не нейтральны. В **нативном lighttpd**, где не существует эквивалентной структуры каталогов, эти относительные пути разрешаются относительно рабочего каталога процесса lighttpd во время выполнения, что редко предсказуемо. Рекомендуется заменить эти 5 строк на абсолютные пути, подходящие для вашей установки, например:
> ```lua
> local blocklist_file         = omega_paths.blocklist_file or "/var/lib/lighttpd/waf/magnet-blocklist.txt"
> local waf_rules_dir          = omega_paths.rules_dir or "/var/lib/lighttpd/waf/magnet-rules.d/"
> local alerts_log             = omega_paths.alerts_log or "/var/log/lighttpd/waf-magnet-alerts.log"
> local blocklist_log          = omega_paths.blocklist_log or "/var/log/lighttpd/waf-magnet-blocklist.log"
> local rate_store_file        = omega_paths.rate_store_file or "/var/cache/lighttpd/waf-magnet-rate_store.lua"
> ```
> Не забудьте создать эти каталоги (и предоставить необходимые права на запись пользователю, от имени которого запускается lighttpd) перед перезапуском.

## Конвейер принятия решений

Скрипт полностью выполняется внутри глобального `pcall`: любая непредвиденная ошибка Lua логируется, после чего возвращается `500`, никогда не обрушивая процесс сервера. Этапы выполняются в этом порядке, каждый может остановить обработку финальным ответом:

1. **Чёрный список** — если IP забанен, запрос отклоняется (`451`), если только запрашиваемый путь явно не в whitelist (например, обслуживает саму страницу ошибки).
2. **Чувствительные пути** — если путь соответствует отслеживаемому шаблону (`.git`, `.env`, `wp-admin`...), в первый раз возвращается HTML-страница предупреждения (`403`); повторение в окне подозрения вызывает бан (`451`).
3. **User-Agent сканера** — если User-Agent соответствует известному инструменту сканирования/боту, в первый раз `403`, при повторении `451`.
4. **Глобальный rate limit** — если превышена глобальная квота по IP, `429`.
5. **Политика SearXNG** — для распознанных поисковых маршрутов: выделенный rate limit (`429`), ограничение размера query-строки (`414`), отклонение нулевых байтов (`451`), затем немедленный выход (`0`, продолжить), чтобы легитимный поиск никогда не проходил через последующие агрессивные проверки.
6. **Защита пути** — поиск SQLi и XSS в декодированном пути (`451` при обнаружении); поиск обхода каталогов (`451`). Намеренно **без** обнаружения инъекции команд на этом этапе (см. [Известные ограничения](#известные-ограничения-и-то-что-вне-рамок)).
7. **Лёгкая защита query-строки** (вне SearXNG) — обход каталогов и нулевой байт (`451`).
8. **Проверка тела POST** — только если `enable_body_inspection` активен и метод — `POST`: слишком большое тело отклоняется напрямую (`413`); иначе накопленная оценка по SQLi/XSS/CMDi/обходу, отказ (`451`), если оценка достигает `waf_score_threshold`, с немедленным баном, если оценка достигает 8, иначе просто подозрительное попадание.
9. **Без блокировки** — запрос продолжается в обычном режиме (`0`).

## Обнаруживаемые сигнатуры

Четыре семейства шаблонов (`patterns`), каждая запись — либо строка (с учётом регистра), либо таблица `{ pat = "шаблон", ci = true }` (без учёта регистра):

- **`sqli_body`**: `UNION SELECT`, `SELECT ... FROM`, `INSERT INTO`, `DROP TABLE`, `OR 1=1`, `' OR '1'='1`, `SLEEP(...)`, `BENCHMARK(...)`, инъекции SQL-команд через точку с запятой (`; DROP`, `; ALTER`, `; EXEC`, `; SHUTDOWN`).
- **`xss_body`**: теги `<script>`, `<iframe>`, атрибуты `on*=` (обработчики событий), `javascript:`, `eval(...)`, `document.cookie`, `svg/onload`.
- **`cmdi_body`**: цепочки shell-команд (`; ls`, `; id`, `; whoami`, `; cat`, `; wget`, `; curl`, `; nc`, `; bash`, `; sh`, `; python`, варианты с `|`), подстановка команд (`` `...` ``, `$(...)`), тег PHP (`<?php`) и функции выполнения (`system(`, `exec(`, `passthru(`).
- **`path_traversal`**: `../`, `..\`, `/proc/self/`, `etc/passwd`, `etc/shadow`, `file://`, `php://filter`.

Плюс отдельный список **User-Agent сканеров/ботов** (`patterns_scanner_ua`): `masscan`, `sqlmap`, `nmap`, `nikto`, `dirbuster`, `wfuzz`, `zgrab`, `python-requests`, `go-http-client`, SEO-краулеры (`ahrefsbot`, `mj12bot`, `semrushbot`, `blexbot`, `dotbot`, `spbot`, `yandexbot`, `sogoubot`), и общие шаблоны (`spider`, `crawler`, `bot`, `scraper`, `facebookexternalhit`, `lwp::simple`).

Декодирование URL применяется рекурсивно (до 5 уровней на пути, 2 уровня на query-строке) перед проверкой, чтобы перехватывать дважды закодированные полезные нагрузки.

## Отслеживаемые чувствительные пути

Шаблоны, проверяемые на декодированном пути: `.env`, `.git`, `.svn`, `.hg`, `.bzr`, `composer.json`/`composer.lock`, `vendor/`, `phpunit/`, `phpmyadmin`/`pma`/`adminer.php`, `wp-admin`/`wp-login.php`, `/server-status`, `.DS_Store`.

Для каждого совпадения скрипт пытается определить, существует ли реально физический ресурс по этому пути (через `lighty.stat`, с резервом на `lighty.c.stat` для совместимости), и указывает это на странице предупреждения и в журнале — полезно для различения слепого сканирования от пути, который действительно существует на сервере.

## Ограничение частоты запросов и эскалация

Два независимых ограничителя частоты запросов, основанных на счётчиках в памяти, персистентных на диске (простое скользящее окно, не точное посекундное скользящее окно):

- **Глобальный**: ключ `g:<ip>`, `global_rate_max_req` запросов за `global_rate_window` секунд, по всем маршрутам.
- **SearXNG**: ключ `sx:<ip>`, `searx_rate_max_req` запросов за `searx_rate_window` секунд, только на распознанных поисковых маршрутах.

Постепенная эскалация (`record_suspicious_hit`) — механизм, отдельный от ограничения частоты запросов: каждое некритичное обнаружение (неповторяющийся чувствительный путь, User-Agent сканера, незначительное попадание в теле POST) увеличивает счётчик по IP (ключ `susp:<ip>`) в окне `suspicious_window` секунд. Как только достигнуто `suspicious_threshold` попаданий в этом окне, IP добавляется в окончательный чёрный список — избегает жёсткого бана за единичное ложное срабатывание, при этом банит рецидивистов.

## Персистентность

| Файл | Содержимое | Формат |
|---|---|---|
| `blocklist_file` | Один забаненный IP на строку, предварённый комментарием с датой (`# дата - причина`) | Простой текст |
| `waf_rules_dir/whitelist_paths.txt` | Один шаблон Lua (`string.match`) на строку, пути, всегда разрешённые даже для забаненного IP | Простой текст |
| `rate_store_file` | Счётчики ограничения частоты и рецидива (`{ count = N, first = timestamp }` на ключ) | Сериализованная таблица Lua (`return { ... }`, перечитывается через `load()`) |
| `alerts_log` | Одна строка на обнаружение/отказ | Читаемый текст, или JSON при `use_json_logs = true` |
| `blocklist_log` | Одна строка на добавление в чёрный список | Читаемый текст |

Файл ограничения частоты никогда не перезаписывается при каждом запросе (только максимум раз в 300 секунд, при периодической очистке), чтобы избежать непропорциональных затрат на I/O. Чёрный список и whitelist кэшируются в памяти и перечитываются максимум раз в `blocklist_refresh_interval`/`whitelist_refresh_interval` секунд — добавление, инициированное самим скриптом, обновляет кэш немедленно, не дожидаясь этой задержки.

## Выдаваемые HTTP-коды ответа

| Код | Значение | Триггер |
|---|---|---|
| `0` | Продолжить обычную обработку (соглашение `mod_magnet`) | Нет обнаружения |
| `403` | Доступ запрещён, первое предупреждение | Обнаружен чувствительный путь (впервые), User-Agent сканера (впервые) |
| `413` | Слишком большая сущность | Тело POST превышает `body_max_inspect` |
| `414` | Слишком длинный URI | Query-строка SearXNG превышает `searx_max_query_len` |
| `429` | Слишком много запросов | Превышен глобальный или SearXNG rate limit |
| `451` | Недоступно по юридическим причинам (здесь используется как код бана) | IP уже забанен, рецидив после эскалации, обнаружен SQLi/XSS/обход в пути или query-строке, нулевой байт, оценка POST ≥ порога |
| `500` | Внутренняя ошибка | Непредвиденное исключение Lua (перехвачено глобальным `pcall`) |

## Совместимость

Скрипт работает в **двух контекстах** без каких-либо изменений:

- **Нативный lighttpd**: `lighty.env`/`lighty.header`/`lighty.content`/`lighty.stat` — нативные API модуля `mod_magnet`. 5 путей конфигурации напрямую используют свои жёстко заданные значения по умолчанию.
- **omega-serv** (`infrastructure/waf/lua_waf_adapter.py`): мост Python-Lua (`lupa`) достоверно воспроизводит тот же контракт `lighty.*`, с **персистентным** Lua-рантаймом между запросами (временные кэши и ограничение частоты запросов, таким образом, корректно сохраняются от запроса к запросу, как и в lighttpd). Глобальная таблица `omega_magnet_paths` инжектируется перед выполнением из конфигурации экрана WAF Magnet, чтобы 5 путей указывали на расположения, выбранные в интерфейсе, а не на жёстко заданные значения.

Никакого расхождения бизнес-логики между двумя контекстами — меняется только источник 5 путей конфигурации.

### Что НЕ совместимо как есть

Скрипт полностью зависит от контракта `lighty.*` (нативного API `mod_magnet`) — он **не** работает как есть на другом сервере, даже если тот предлагает какую-то форму Lua-скриптинга:

- **Apache** (`mod_lua`): другой API, основанный на объекте запроса `r` (`r.method`, `r.uri`, `r.headers_in`, `r:puts(...)`) — ни один вызов `lighty.*` не сработал бы.
- **nginx** (`lua-nginx-module` / OpenResty): другой API (`ngx.var`, `ngx.req`, `ngx.header`, `ngx.exit()`), с моделью фаз выполнения (`access_by_lua`, `content_by_lua`...), отличной от простого возврата кода `mod_magnet`.
- **Traefik**: вообще нет нативного Lua-скриптинга (написан на Go) — только Go-плагин (Yaegi) позволил бы выполнять пользовательскую логику, но никогда напрямую Lua.
- **Caddy**: нет официального модуля Lua — потребовался бы сторонний плагин, скомпилированный через `xcaddy`, ничего эквивалентного нативно не доступно.

Сделать этот скрипт совместимым с одним из этих серверов потребовало бы написания выделенного моста совместимости, транслирующего его нативный API в `lighty.*` (именно то, что делает `lua_waf_adapter.py` для omega-serv) — отдельная инженерная работа, а не простая настройка конфигурации.

## Настройка

- **Адаптация под другое приложение, не SearXNG**: изменить `is_searxng_path()` (список путей) и, при необходимости, полностью убрать раздел 3 конвейера (выделенная политика), если защищаемому приложению не нужна дифференцированная обработка поисков.
- **Добавление всегда разрешённых путей**: отредактировать `waf_rules_dir/whitelist_paths.txt` (один шаблон Lua на строку), или добавить жёстко заданное исключение в `is_whitelisted_path()`.
- **Настройка агрессивности**: `waf_score_threshold` (порог отказа POST), `suspicious_threshold`/`suspicious_window` (скорость эскалации к окончательному бану), `global_rate_max_req`/`global_rate_window` (общий rate limit).
- **Переключение журналов на JSON** (приём SIEM/log shipper): `use_json_logs = true`.
- **Отключение подсистемы без затрагивания остального**: `enable_body_inspection`, `enable_rate_limit`, `enable_auto_block` независимы.

## Известные ограничения и то, что вне рамок

- **Нет обнаружения CMDi в пути URL**: осознанный выбор, чтобы избежать ложных срабатываний на путях, содержащих `.php` (который был бы спутан с `<?php`, если бы обнаружение CMDi включало тег PHP на этой поверхности). Обнаружение CMDi остаётся активным в теле POST.
- **Сигнатуры через сопоставление шаблонов Lua, а не настоящий движок PCRE**: варианты атак, не покрытые перечисленными шаблонами, не будут обнаружены — это не замена WAF на основе исчерпывающих наборов правил (например, CRS ModSecurity).
- **Нет разбора multipart/form-data**: вредоносная полезная нагрузка, инкапсулированная в поле multipart-формы, может избежать проверки, если шаблоны не совпадают с необработанным, недекодированным потоком.
- **Нет распаковки gzip тела**: сжатое тело не проверяется в открытом виде.
- **Приблизительное ограничение частоты запросов**: упрощённое скользящее окно (полный сброс при превышении окна), а не точный алгоритм скользящего окна (sliding log/token bucket).
- **Нет интерфейса наблюдения**: всё наблюдение проходит через прямое чтение файлов журналов и чёрного списка.

## Устранение неполадок

- **Скрипт, похоже, никогда не выполняется**: проверьте, что `mod_magnet` действительно загружен (lighttpd) или что дополнение `magnet` установлено, а WAF Magnet включён (omega-serv); перезагрузки конфигурации никогда не достаточно для загрузки изменённого Lua-скрипта, в обоих случаях требуется полный перезапуск.
- **Счётчики rate limit, похоже, сбрасываются при каждом запросе**: симптом непостоянного Lua-рантайма между запросами (скрипт начинает заново с пустым `rate_store` при каждом выполнении) — под omega-serv проверьте, что экран WAF Magnet сообщает об активном персистентном рантайме.
- **Легитимный IP оказывается забанен**: посмотрите `blocklist_log` и `alerts_log`, чтобы определить сработавшее правило, настройте соответствующий шаблон или порог, затем удалите строку IP в `blocklist_file` (кэш в памяти обновится при следующем обновлении, максимум через `blocklist_refresh_interval` секунд после изменения файла).
- **Легитимные поисковые запросы SearXNG блокируются**: проверьте `is_searxng_path()` (нераспознанный путь) перед настройкой выделенных порогов rate limit.
