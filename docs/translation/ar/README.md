**Omega-Waf** سكربت Lua واحد (`omega-waf.lua`)، دون أي اعتمادية خارجية، مصمَّم ليُنفَّذ عند كل طلب HTTP بواسطة خادم ويب متوافق مع `mod_magnet` (lighttpd أصلًا، أو omega-serv عبر جسر التوافق `magnet` الخاص به). يفحص المسار والطلب، وفي حالة POST جسم الطلب، بحثًا عن تواقيع هجمات معروفة (حقن SQL، وXSS، وحقن الأوامر، واجتياز المجلدات)، ويطبّق تحديد المعدل، ويدير قائمة حظر دائمة مع تصعيد تدريجي، ويسجّل كل قرار.

لا تثبيت بالمعنى التقليدي: ملف واحد تضعه، وتشير إليه من تهيئة الخادم، وهذا كل شيء.

## نظرة عامة

### الأهداف

- تصفية الطلبات الخبيثة في أقرب نقطة ممكنة من الخادم، قبل أن تصل إلى التطبيق المقدَّم.
- البقاء ملفًا واحدًا مقروءًا، دون اعتمادية خارجية ولا خطوة تصريف.
- عدم إسقاط خادم الويب أبدًا: يُلتقط أي خطأ داخلي في السكربت ويُسجَّل بدلًا من أن ينتشر.
- الحد من كلفة المعالج/الذاكرة لكل طلب (تخزين مؤقت زمني، وقراءة الجسم على أجزاء، وعمق فك ترميز محدود).
- توفير تصعيد تدريجي (تحذير ثم حظر) بدلًا من حظر قاطع عند أول حادث بسيط.

### ما يفعله Omega-Waf

- يحجب عناوين IP المحظورة مسبقًا (قائمة حظر دائمة على القرص)، مع استثناء للمسارات المسموح بها صراحةً (ملف CSS لصفحة الخطأ، إلخ).
- يراقب مجموعة من المسارات الحساسة (`.git`، `.env`، `wp-admin`، `phpmyadmin`، `.DS_Store`، إلخ) ويرد إما بصفحة تحذير HTML، وإما بحظر مباشر عند التكرار.
- يكتشف قيم User-Agent المعروفة بأنها أدوات مسح أو روبوتات غير مرغوب فيها (sqlmap، nmap، nikto، dirbuster، زواحف عامة...).
- يطبّق تحديد معدل عامًا لكل IP، على جميع المسارات مجتمعة.
- يطبّق سياسة مخصصة، أكثر تساهلًا، على مسارات محرك بحث SearXNG (لتجنّب الإنذارات الكاذبة على طلبات بحث مشروعة تحتوي على كلمات مفتاحية قد تبدو كهجوم).
- يفحص المسار وسلسلة الاستعلام (query-string) (SQLi، XSS، اجتياز المجلدات، بايت NUL).
- يفحص جسم طلبات POST (SQLi، XSS، حقن الأوامر، اجتياز المجلدات) بنظام درجات تراكمي.
- يدير تصعيدًا تدريجيًا: سلوك مريب منفرد يطلق تنبيهًا أو رفضًا عرضيًا؛ والتكرار ضمن نافذة زمنية يطلق حظرًا نهائيًا.
- يسجّل كل قرار (التنبيهات، والإضافات إلى قائمة الحظر) بتنسيق نصي أو JSON.
- يعمل سواء في lighttpd الأصلي (مسارات مكتوبة في الشيفرة) أو محقونًا في omega-serv (مسارات تُستلم ديناميكيًا من تهيئة الخادم).

### ما لا يفعله السكربت

- لا يحل محل جدار حماية تطبيقات (WAF) مخصص على مستوى المؤسسات (ModSecurity، Coraza، WAF سحابي): التواقيع بسيطة عمدًا (مطابقة أنماط Lua، لا محرك قواعد PCRE حقيقي).
- لا يحلّل ترويسات HTTP واحدة تلو الأخرى فيما عدا User-Agent.
- لا يفك ترميز الأجسام من نوع multipart/form-data ولا الأجسام المضغوطة (gzip) — يجري الفحص على النص الخام المستلَم.
- لا يفحص أبدًا جسم طلب غير POST.
- لا يكتشف حقن الأوامر في مسار URL (خيار متعمَّد، انظر [القيود المعروفة](#القيود-المعروفة-وما-هو-خارج-النطاق)).
- لا يوفّر أي واجهة إدارة: تجري التهيئة بتحرير المتغيرات في رأس الملف، وقائمة الحظر والقائمة البيضاء عبر ملفات نصية بسيطة.
- لا يتولى بنفسه تدوير سجلاته.

### تحذير الاستخدام

تستهدف التواقيع المقدَّمة عائلات الهجمات الشائعة لكنها لا تشكّل حماية شاملة. قد تؤدي درجة كشف منخفضة جدًا على موقع ذي حركة غير معتادة (بحث تقني، توثيق يحتوي على أوامر shell، إلخ) إلى إنذارات كاذبة — اضبط `waf_score_threshold` والقائمة البيضاء للمسارات وفقًا لذلك. اختبر دائمًا أي تغيير في التواقيع أو العتبات في بيئة غير حرجة قبل نشره في الإنتاج.

## التثبيت

### المتطلبات المسبقة

- خادم ويب يوفّر واجهة متوافقة مع `mod_magnet`:
  - **lighttpd** مع تفعيل الوحدة `mod_magnet` (`server.modules += ("mod_magnet")`)، أو
  - **omega-serv** مع تثبيت الإضافة `magnet` (الاعتمادية `lupa` — انظر أدناه ودليل omega-serv، قسم WAF Magnet).
- مفسّر Lua مضمَّن يوفّره المضيف (يضمّن lighttpd مفسّر Lua الخاص به؛ ويضمّن omega-serv `lupa`، ولا حاجة في الحالتين إلى مفسّر `lua` في النظام — تُوزَّع `lupa` كحزمة wheel مُصرَّفة مسبقًا لجميع المعماريات/إصدارات Python الشائعة، دون تصريف محلي ولا ملفات ترويسة Lua في النظام).

#### تثبيت إضافة `magnet` في omega-serv

**دائمًا من `.venv` الذي أنشأه `omega-serv/install.sh` مسبقًا، وليس أبدًا بـ `pip` النظام** — في بعض التوزيعات (ولا سيما Arch Linux)، إما أن الأمر `pip` المجرد غير موجود (لا تثبّته إلا الحزمة `python-pip`، وليس بالضرورة افتراضيًا) وإما أنه يرفض تثبيت أي شيء خارج بيئة افتراضية (`error: externally-managed-environment`، PEP 668):

```bash
cd /path/to/omega-serv

# الخيار A - البيئة الافتراضية venv مفعّلة مسبقًا في الصدفة الحالية
source .venv/bin/activate
pip install -e ".[magnet]"

# الخيار B - دون تفعيل venv (الطريقة الأكثر قابلية للنقل: لا تعتمد أبدًا
# على وجود 'pip' أو غيابه في PATH النظام، لأن python الخاص
# بالـ venv يحمل دائمًا pip الخاص به)
.venv/bin/python -m pip install -e ".[magnet]"
```

إذا لم يُشغَّل `install.sh` بعد (لا يوجد `.venv/`)، فشغّله أولًا — فهو ينشئ البيئة الافتراضية ويثبّت فيها omega-serv نفسه؛ ولا يبقى عندئذ إلا إضافة `magnet` (الاختيارية) بأحد الأمرين أعلاه.

### خطوات الإعداد

1. انسخ `omega-waf.lua` إلى موقع يستطيع الخادم قراءته (مثل `secure/waf/scripts/omega-waf.lua` لهيكل على طريقة omega-serv، أو أي مسار في lighttpd الأصلي).
2. أنشئ المجلدات/الملفات المتوقعة:
   - **omega-serv**: لا شيء لتفعله، فالخادم ينشئ المجلدات بنفسه عند البدء (ومنها `var/lib/waf/`، المشترك مع حساب الخدمة).
   - **lighttpd الأصلي**: استبدل أولًا المسارات الخمسة بمسارات مطلقة (انظر [المسارات في lighttpd الأصلي](#المسارات-في-lighttpd-الأصلي))، ثم أنشئ المجلدات واجعلها قابلة للكتابة من حساب lighttpd (`www-data` في Debian/Ubuntu، و`http` في Arch، و`lighttpd` في Fedora/Alpine):
     ```bash
     sudo install -d -o www-data -g www-data -m 750 /var/lib/lighttpd/waf /var/log/lighttpd /var/cache/lighttpd
     sudo install -d -m 755 /var/lib/lighttpd/waf/magnet-rules.d
     sudo -u www-data touch /var/lib/lighttpd/waf/magnet-blocklist.txt
     ```
3. أشر إلى السكربت من تهيئة الخادم:
   - **lighttpd**:
     ```
     magnet.attract-physical-path-to = ( "/path/to/omega-waf.lua" )
     ```
   - **omega-serv**: فعّل WAF Magnet من شاشة TUI المخصصة (الأمان النشط → WAF → Magnet)، التي تشير إلى السكربت وتحقن تلقائيًا الجدول `omega_magnet_paths` (انظر [التوافق](#التوافق)).
4. أعد تشغيل الخادم المعني (وليس إعادة التحميل — فإعادة التحميل لا تعيد أبدًا تحميل سكربت Lua موجود مسبقًا في الذاكرة الدائمة).

## التهيئة

تُضبط جميع الخيارات بتعديل المتغيرات المحلية مباشرة في رأس الملف (القسم `CONFIGURATION`، الأسطر ~24-70). لا يوجد ملف تهيئة منفصل.

| المتغير | الدور | القيمة الافتراضية |
|---|---|---|
| `blocklist_file` | ملف نصي لعناوين IP المحظورة نهائيًا (عنوان IP واحد في كل سطر، `#` للتعليق) — **يكتب فيه** السكربت | `var/lib/waf/magnet-blocklist.txt` |
| `waf_rules_dir` | مجلد القواعد الخارجية (يحتوي على `whitelist_paths.txt`) | `secure/waf/magnet-rules.d/` |
| `alerts_log` | سجل التنبيهات (الاكتشافات، والرفض، والتجاوزات) | `var/log/waf-magnet-alerts.log` |
| `blocklist_log` | سجل مخصص للإضافات إلى قائمة الحظر | `var/log/waf-magnet-blocklist.log` |
| `rate_store_file` | ملف حفظ العدادات (تحديد المعدل / التكرار)، بتنسيق جدول Lua | `var/cache/waf-magnet-rate_store.lua` |
| `enable_body_inspection` | يفعّل فحص جسم طلبات POST | `true` |
| `enable_rate_limit` | يفعّل تحديد المعدل (العام + SearXNG) | `true` |
| `enable_auto_block` | يسمح بالإضافة التلقائية إلى قائمة الحظر | `true` |
| `never_auto_block` | شبكات **لا** تُحظر تلقائيًا **أبدًا** (يبقى الطلب مرفوضًا ومسجَّلًا، ويُتجنَّب الحظر وحده)؛ في omega-serv، تكون الأولوية دائمًا للقائمة التي يحقنها الخادم (`omega_never_auto_block`) | المضيف المحلي، وTailscale، والشبكات المحلية |
| `use_json_logs` | يحوّل سجلات التنبيه إلى JSON (وإلا فنص مقروء) | `false` |
| `waf_score_threshold` | الحد الأدنى للدرجة التراكمية لرفض طلب POST | `5` |
| `body_max_inspect` | الحجم الأقصى المفحوص من الجسم (بالبايت) | `65536` (64 كيلوبايت) |
| `chunk_size` | حجم كتل قراءة الجسم | `8192` (8 كيلوبايت) |
| `global_rate_max_req` / `global_rate_window` | حصة ونافذة (ث) تحديد المعدل العام لكل IP | `60` طلبًا / `60` ث |
| `searx_rate_max_req` / `searx_rate_window` | حصة ونافذة (ث) تحديد المعدل المخصص لمسارات SearXNG | `40` طلبًا / `60` ث |
| `searx_max_query_len` | الحجم الأقصى المقبول لسلسلة الاستعلام على مسارات SearXNG | `4096` حرفًا |
| `suspicious_threshold` | عدد الإصابات المريبة قبل الحظر النهائي | `3` |
| `suspicious_window` | النافذة المنزلقة (ث) التي تُحسب عليها الإصابات المريبة | `300` (5 دقائق) |
| `blocklist_refresh_interval` | الفاصل الزمني (ث) لإعادة قراءة ملف قائمة الحظر | `5` |
| `whitelist_refresh_interval` | الفاصل الزمني (ث) لإعادة قراءة القائمة البيضاء للمسارات | `15` |

في omega-serv، تُستبدل المسارات الخمسة الأولى (`blocklist_file`، `waf_rules_dir`، `alerts_log`، `blocklist_log`، `rate_store_file`) تلقائيًا بتلك المهيأة في شاشة WAF Magnet (الجدول العام `omega_magnet_paths` المحقون قبل التنفيذ) — ولا تُستخدم القيم المكتوبة في الشيفرة أعلاه عندئذ إلا كقيم احتياطية إذا غاب هذا الجدول.

> ℹ️ **تغيير بتاريخ 2026-10-18**: ينتقل `blocklist_file` من `secure/waf/magnet-blocklist.txt` إلى `var/lib/waf/magnet-blocklist.txt`. يكتب السكربت **في** هذا الملف عند كل حظر، ولا تستطيع خدمة systemd الخاصة بـ omega-serv الكتابة إلا تحت `var/`: مع الموقع القديم، لم يكن أي حظر تلقائي يُسجَّل أبدًا، دون أي رسالة. يستعيد omega-serv الملف القديم مرة واحدة عند البدء (ويبقى القديم في مكانه كنسخة احتياطية)؛ ولا يُعدَّل أبدًا مسار مخصص مضبوط في شاشة WAF Magnet.

### المسارات في lighttpd الأصلي

> ⚠️ **هذه القيم الافتراضية الخمس مأخوذة عن اصطلاح المجلدات الخاص بـ omega-serv** (`var/lib/waf/...`، `secure/waf/...`، `var/log/...`، `var/cache/...`، مسارات نسبية تُحَل بالنسبة إلى مجلد عمل من نوع المشروع) — فهي ليست محايدة. في **lighttpd الأصلي**، حيث لا يوجد اصطلاح مجلدات مكافئ، تُحَل هذه المسارات النسبية بالنسبة إلى مجلد عمل عملية lighttpd وقت التشغيل (غالبًا `/`)، وهو نادرًا ما يمكن توقعه. **استبدل هذه الأسطر الخمسة بمسارات مطلقة** تناسب تثبيتك، على سبيل المثال:
> ```lua
> local blocklist_file         = omega_paths.blocklist_file or "/var/lib/lighttpd/waf/magnet-blocklist.txt"
> local waf_rules_dir          = omega_paths.rules_dir or "/var/lib/lighttpd/waf/magnet-rules.d/"
> local alerts_log             = omega_paths.alerts_log or "/var/log/lighttpd/waf-magnet-alerts.log"
> local blocklist_log          = omega_paths.blocklist_log or "/var/log/lighttpd/waf-magnet-blocklist.log"
> local rate_store_file        = omega_paths.rate_store_file or "/var/cache/lighttpd/waf-magnet-rate_store.lua"
> ```
> قبل إعادة التشغيل، أنشئ هذه المجلدات (الأوامر في الخطوة 2 من [خطوات الإعداد](#خطوات-الإعداد)) مع احترام هذه الأذونات:
>
> | الملف | الوصول اللازم لحساب lighttpd |
> |---|---|
> | `blocklist_file`، `alerts_log`، `blocklist_log`، `rate_store_file` | **كتابة** (الملف والمجلد الذي يحتويه) |
> | `waf_rules_dir` (و`whitelist_paths.txt`) | قراءة فقط |
>
> فشل الكتابة **صامت** — فالسكربت لا يعطّل الطلب أبدًا —: الحظر الذي لا يظهر في `blocklist_file` هو العَرَض الوحيد. تحقّق بالأمر `sudo -u www-data touch /var/lib/lighttpd/waf/magnet-blocklist.txt` (مع تكييف اسم الحساب). إذا كانت وحدة systemd الخاصة بـ lighttpd تقيّد الكتابة (`ProtectSystem=strict`، `ReadWritePaths=`)، فأضف إليها هذه المجلدات.

## مسار اتخاذ القرار

يُنفَّذ السكربت بالكامل داخل `pcall` عام: يُسجَّل أي خطأ Lua غير متوقع ثم يُرد بـ `500`، دون أن تنهار عملية الخادم أبدًا. تُنفَّذ الخطوات بهذا الترتيب، ويمكن لكل منها إيقاف المعالجة باستجابة نهائية:

1. **قائمة الحظر** — إذا كان عنوان IP محظورًا، يُرفض الطلب (`451`)، إلا إذا كان المسار المطلوب مدرجًا صراحةً في القائمة البيضاء (يقدّم مثلًا صفحة الخطأ نفسها).
2. **المسارات الحساسة** — إذا طابق المسار نمطًا مراقَبًا (`.git`، `.env`، `wp-admin`...)، تُعاد صفحة تحذير HTML (`403`) في المرة الأولى؛ ويطلق التكرار ضمن نافذة الاشتباه حظرًا (`451`).
3. **User-Agent لأداة مسح** — إذا طابق User-Agent أداة مسح/روبوتًا معروفًا، `403` في المرة الأولى، و`451` عند التكرار.
4. **تحديد المعدل العام** — إذا تجاوز عنوان IP الحصة العامة، `429`.
5. **سياسة SearXNG** — لمسارات البحث المعروفة: تحديد معدل مخصص (`429`)، وحاجز لحجم سلسلة الاستعلام (`414`)، ورفض بايتات NUL (`451`)، ثم خروج فوري (`0`، متابعة) كي لا يخضع أي بحث مشروع أبدًا للفحوص الصارمة التالية.
6. **حماية المسار** — البحث عن SQLi وXSS في المسار بعد فك ترميزه (`451` عند الاكتشاف)؛ والبحث عن اجتياز المجلدات (`451`). **لا** كشف لحقن الأوامر عمدًا في هذه الخطوة (انظر [القيود المعروفة](#القيود-المعروفة-وما-هو-خارج-النطاق)).
7. **حماية خفيفة لسلسلة الاستعلام** (خارج SearXNG) — اجتياز المجلدات وبايت NUL (`451`).
8. **فحص جسم POST** — فقط إذا كان `enable_body_inspection` مفعّلًا وكانت الطريقة `POST`: يُرفض الجسم الكبير جدًا مباشرة (`413`)؛ وإلا فدرجة تراكمية على SQLi/XSS/CMDi/الاجتياز، مع الرفض (`451`) إذا بلغت الدرجة `waf_score_threshold`، وحظر فوري إذا بلغت الدرجة 8، وإلا فمجرد إصابة مريبة.
9. **لا حجب** — يستمر الطلب بشكل طبيعي (`0`).

## التواقيع المكتشفة

أربع عائلات من الأنماط (`patterns`)، وكل مدخل إما سلسلة نصية (حساسة لحالة الأحرف)، وإما جدول `{ pat = "pattern", ci = true }` (غير حساس لحالة الأحرف):

- **`sqli_body`**: `UNION SELECT`، `SELECT ... FROM`، `INSERT INTO`، `DROP TABLE`، `OR 1=1`، `' OR '1'='1`، `SLEEP(...)`، `BENCHMARK(...)`، حقن أوامر SQL عبر الفاصلة المنقوطة (`; DROP`، `; ALTER`، `; EXEC`، `; SHUTDOWN`).
- **`xss_body`**: الوسوم `<script>` و`<iframe>`، والسمات `on*=` (معالجات الأحداث)، `javascript:`، `eval(...)`، `document.cookie`، `svg/onload`.
- **`cmdi_body`**: تسلسل أوامر shell (`; ls`، `; id`، `; whoami`، `; cat`، `; wget`، `; curl`، `; nc`، `; bash`، `; sh`، `; python`، وصيغ مع `|`)، واستبدال الأوامر (`` `...` ``، `$(...)`)، ووسم PHP (`<?php`) ودوال التنفيذ (`system(`، `exec(`، `passthru(`).
- **`path_traversal`**: `../`، `..\`، `/proc/self/`، `etc/passwd`، `etc/shadow`، `file://`، `php://filter`.

إضافة إلى قائمة مخصصة **لقيم User-Agent الخاصة بأدوات المسح/الروبوتات** (`patterns_scanner_ua`): `masscan`، `sqlmap`، `nmap`، `nikto`، `dirbuster`، `wfuzz`، `zgrab`، `python-requests`، `go-http-client`، وزواحف تحسين محركات البحث (`ahrefsbot`، `mj12bot`، `semrushbot`، `blexbot`، `dotbot`، `spbot`، `yandexbot`، `sogoubot`)، وأنماط عامة (`spider`، `crawler`، `bot`، `scraper`، `facebookexternalhit`، `lwp::simple`).

يُطبَّق فك ترميز URL بشكل متكرر (حتى 5 مستويات على المسار، ومستويين على سلسلة الاستعلام) قبل الفحص، لالتقاط الحمولات المرمَّزة مرتين.

## تحديد المعدل والتصعيد

محدِّدا معدل مستقلان، يعتمدان على عدادات في الذاكرة تُحفظ على القرص (نافذة منزلقة بسيطة، لا نافذة منزلقة دقيقة بالثانية):

- **العام**: المفتاح `g:<ip>`، و`global_rate_max_req` طلبًا كل `global_rate_window` ثانية، على جميع المسارات مجتمعة.
- **SearXNG**: المفتاح `sx:<ip>`، و`searx_rate_max_req` طلبًا كل `searx_rate_window` ثانية، فقط على مسارات البحث المعروفة.

التصعيد التدريجي (`record_suspicious_hit`) آلية منفصلة عن تحديد المعدل: كل اكتشاف غير حرج (مسار حساس دون تكرار، User-Agent لأداة مسح، إصابة طفيفة في جسم POST) يزيد عدادًا لكل IP (المفتاح `susp:<ip>`) على نافذة من `suspicious_window` ثانية. وبمجرد بلوغ `suspicious_threshold` إصابة ضمن هذه النافذة، يُضاف عنوان IP إلى قائمة الحظر النهائية — ما يتجنّب حظرًا قاطعًا بسبب إنذار كاذب واحد، مع حظر المكرِّرين في الوقت نفسه.

**شبكات لا تُحظر أبدًا**: عنوان من `never_auto_block` (المضيف المحلي، وTailscale `100.64.0.0/10`، والشبكات المحلية IPv4/IPv6، بما في ذلك صيغة IPv4-mapped-IPv6) لا يطلق أبدًا تصعيدًا ولا إضافة إلى قائمة الحظر؛ ويُتتبَّع الحظر الذي جرى تجنّبه بسطر `BAN EVITE` في `blocklist_log` (وليس أبدًا `AJOUT BLOCKLIST`، الذي يقرؤه omega-jail). مقارنة CIDR بلغة Lua محمولة، من 5.1 إلى 5.5 وLuaJIT.

**وضع log-only في omega-serv**: عندما يكون WAF الخاص بـ omega-serv في وضع `log-only`، لا يضع السكربت أي حظر (لا قائمة حظر ولا سطر `AJOUT BLOCKLIST`، وبالتالي لا حظر على مستوى الشبكة عبر fail2ban)؛ ويسجّل ذلك سطر `BAN EVITE`. وإذا تعذّرت كتابة قائمة الحظر، يحلّ سطر `ECHEC BLOCKLIST` محلّ `AJOUT BLOCKLIST`.

## الحفظ الدائم

| الملف | المحتوى | التنسيق |
|---|---|---|
| `blocklist_file` | عنوان IP محظور واحد في كل سطر، يسبقه تعليق مؤرَّخ (`# date - reason`) | نص خام |
| `waf_rules_dir/whitelist_paths.txt` | نمط Lua واحد (`string.match`) في كل سطر، لمسارات مسموح بها دائمًا حتى لعنوان IP محظور | نص خام |
| `rate_store_file` | عدادات تحديد المعدل والتكرار (`{ count = N, first = timestamp }` لكل مفتاح) | جدول Lua مُسلسَل (`return { ... }`، يُعاد قراءته عبر `load()`) |
| `alerts_log` | سطر واحد لكل اكتشاف/رفض | نص مقروء، أو JSON إذا كان `use_json_logs = true` |
| `blocklist_log` | سطر واحد لكل إضافة إلى قائمة الحظر | نص مقروء |

لا يُعاد أبدًا كتابة ملف تحديد المعدل عند كل طلب (بل على الأكثر مرة كل 300 ثانية، أثناء التنظيف الدوري) لتجنّب كلفة إدخال/إخراج غير متناسبة. تُخزَّن قائمة الحظر والقائمة البيضاء مؤقتًا في الذاكرة ويُعاد قراءتهما على الأكثر كل `blocklist_refresh_interval`/`whitelist_refresh_interval` ثانية — والإضافة التي يطلقها السكربت نفسه تحدّث التخزين المؤقت فورًا، دون انتظار هذه المهلة.

## رموز استجابة HTTP الصادرة

| الرمز | المعنى | المُطلِق |
|---|---|---|
| `0` | متابعة المعالجة العادية (اصطلاح `mod_magnet`) | لا اكتشاف |
| `403` | الوصول مرفوض، تحذير أول | اكتشاف مسار حساس (المرة الأولى)، User-Agent لأداة مسح (المرة الأولى) |
| `413` | الحمولة كبيرة جدًا | جسم POST يتجاوز `body_max_inspect` |
| `414` | URI طويل جدًا | سلسلة استعلام SearXNG تتجاوز `searx_max_query_len` |
| `429` | طلبات كثيرة جدًا | تجاوز تحديد المعدل العام أو الخاص بـ SearXNG |
| `451` | غير متاح لأسباب قانونية (يُستخدم هنا رمزًا للحظر) | عنوان IP محظور مسبقًا، تكرار بعد التصعيد، اكتشاف SQLi/XSS/اجتياز في المسار أو سلسلة الاستعلام، بايت NUL، درجة POST ≥ العتبة |
| `500` | خطأ داخلي | استثناء Lua غير متوقع (يلتقطه `pcall` العام) |

## التوافق

يعمل السكربت في **سياقين**، دون أي تعديل على الإطلاق:

- **lighttpd الأصلي**: `lighty.env`/`lighty.header`/`lighty.content`/`lighty.stat` هي واجهات API الأصلية للوحدة `mod_magnet`. وتستخدم مسارات التهيئة الخمسة قيمها الافتراضية المكتوبة في الشيفرة مباشرة.
- **omega-serv** (`infrastructure/waf/lua_waf_adapter.py`): جسر Python-Lua (`lupa`) يعيد إنتاج عقد `lighty.*` نفسه بأمانة، مع بيئة تشغيل Lua **دائمة** بين الطلبات (لذا تبقى ذاكرات التخزين المؤقت الزمنية وتحديد المعدل قائمة بشكل صحيح من طلب إلى آخر، تمامًا كما في lighttpd). يُحقن الجدول العام `omega_magnet_paths` قبل التنفيذ من تهيئة شاشة WAF Magnet، كي تشير المسارات الخمسة إلى المواقع المختارة في الواجهة بدلًا من القيم المكتوبة في الشيفرة.

لا اختلاف في منطق العمل بين السياقين — وحده مصدر مسارات التهيئة الخمسة يتغير.

### ما ليس متوافقًا كما هو

يعتمد السكربت كليًا على عقد `lighty.*` (واجهة API الأصلية لـ `mod_magnet`) — فهو **لا** يعمل كما هو على خادم آخر، حتى لو كان يوفّر شكلًا من أشكال البرمجة النصية بـ Lua:

- **Apache** (`mod_lua`): واجهة API مختلفة، مبنية على كائن طلب `r` (`r.method`، `r.uri`، `r.headers_in`، `r:puts(...)`) — لن يعمل أي استدعاء `lighty.*`.
- **nginx** (`lua-nginx-module` / OpenResty): واجهة API مختلفة (`ngx.var`، `ngx.req`، `ngx.header`، `ngx.exit()`)، مع نموذج مراحل تنفيذ (`access_by_lua`، `content_by_lua`...) يختلف عن مجرد إرجاع رمز في `mod_magnet`.
- **Traefik**: لا برمجة نصية أصلية بـ Lua على الإطلاق (مكتوب بلغة Go) — وحدها إضافة Go (Yaegi) يمكنها تنفيذ منطق مخصص، وليس Lua مباشرة أبدًا.
- **Caddy**: لا وحدة Lua رسمية — سيتطلب ذلك إضافة من طرف ثالث تُصرَّف عبر `xcaddy`، ولا يتوفر أي مكافئ أصليًا.

جعل هذا السكربت متوافقًا مع أحد هذه الخوادم يتطلب كتابة جسر توافق مخصص يترجم واجهة API الأصلية للخادم إلى `lighty.*` (وهو بالضبط ما يفعله `lua_waf_adapter.py` لـ omega-serv) — عمل هندسي قائم بذاته، لا مجرد تكييف للتهيئة.

## التخصيص

- **التكييف مع تطبيق آخر غير SearXNG**: عدّل `is_searxng_path()` (قائمة المسارات)، وإن لزم الأمر، احذف القسم 3 من المسار بالكامل (السياسة المخصصة) إذا كان التطبيق المحمي لا يحتاج إلى معالجة مختلفة لعمليات البحث.
- **إضافة مسارات مسموح بها دائمًا**: حرّر `waf_rules_dir/whitelist_paths.txt` (نمط Lua واحد في كل سطر)، أو أضف استثناءً مكتوبًا في الشيفرة في `is_whitelisted_path()`.
- **ضبط درجة الصرامة**: `waf_score_threshold` (عتبة رفض POST)، و`suspicious_threshold`/`suspicious_window` (سرعة التصعيد نحو الحظر النهائي)، و`global_rate_max_req`/`global_rate_window` (تحديد المعدل العام).
- **تحويل السجلات إلى JSON** (للاستيعاب في SIEM/log shipper): `use_json_logs = true`.
- **تعطيل نظام فرعي دون المساس بالباقي**: `enable_body_inspection` و`enable_rate_limit` و`enable_auto_block` مستقلة بعضها عن بعض.

## القيود المعروفة وما هو خارج النطاق

- **لا كشف لـ CMDi في مسار URL**: خيار متعمَّد لتجنّب الإنذارات الكاذبة على المسارات التي تحتوي على `.php` (الذي كان سيُخلط مع `<?php` لو شمل كشف CMDi وسم PHP على هذا السطح). ويبقى كشف CMDi نشطًا على جسم POST.
- **تواقيع بمطابقة أنماط Lua، لا محرك PCRE حقيقي**: لن تُكتشف صيغ الهجمات غير المشمولة بالأنماط المدرجة — فهذا ليس بديلًا عن WAF قائم على مجموعات قواعد شاملة (من نوع ModSecurity CRS).
- **لا تحليل لـ multipart/form-data**: قد تفلت حمولة خبيثة مغلّفة في حقل نموذج multipart من الفحص إذا لم تطابق الأنماطُ التدفقَ الخام غير المفكوك ترميزه.
- **لا فك ضغط gzip للجسم**: لا يُفحص الجسم المضغوط بشكل صريح.
- **تحديد معدل تقريبي**: نافذة منزلقة مبسّطة (إعادة تعيين كاملة عند تجاوز النافذة)، لا خوارزمية نافذة منزلقة دقيقة (sliding log/token bucket).
- **لا واجهة إشراف**: كل مراقبة تمر عبر القراءة المباشرة لملفات السجل وقائمة الحظر.

## استكشاف الأخطاء وإصلاحها

- **يبدو أن السكربت لا يُنفَّذ أبدًا**: تحقّق من أن `mod_magnet` محمَّل فعلًا (lighttpd) أو من أن الإضافة `magnet` مثبّتة وأن WAF Magnet مفعّل (omega-serv)؛ فإعادة تحميل التهيئة لا تكفي أبدًا لتحميل سكربت Lua معدَّل، ويلزم إعادة تشغيل كاملة في الحالتين.
- **يبدو أن عدادات تحديد المعدل تُعاد إلى الصفر مع كل طلب**: عَرَض لبيئة تشغيل Lua غير دائمة بين الطلبات (يبدأ السكربت من `rate_store` فارغ عند كل تنفيذ) — في omega-serv، تحقّق من أن شاشة WAF Magnet تشير فعلًا إلى بيئة تشغيل دائمة نشطة.
- **عنوان IP مشروع يجد نفسه محظورًا**: راجع `blocklist_log` و`alerts_log` لتحديد القاعدة التي انطلقت، واضبط النمط أو العتبة المقابلة، ثم احذف سطر عنوان IP من `blocklist_file` (يتحدّث التخزين المؤقت في الذاكرة عند إعادة القراءة التالية، بعد `blocklist_refresh_interval` ثانية على الأكثر من تعديل الملف).
- **عمليات بحث SearXNG المشروعة محجوبة**: تحقّق من `is_searxng_path()` (مسار غير معروف) قبل ضبط عتبات تحديد المعدل المخصصة.
- **يفشل `pip install -e ".[magnet]"` مع `pip: command not found` أو `externally-managed-environment`**: كُتب الأمر خارج `.venv` الخاص بـ omega-serv (بعض التوزيعات، ولا سيما Arch Linux، لا توفّر أي `pip` نظام قابل للاستخدام مباشرة). استخدم بدلًا من ذلك `.venv/bin/python -m pip install -e ".[magnet]"` من مجلد omega-serv — يعمل دون الاعتماد على وجود `pip` في `PATH` النظام (انظر [تثبيت إضافة `magnet` في omega-serv](#تثبيت-إضافة-magnet-في-omega-serv)).
